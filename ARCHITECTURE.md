# Architecture

How each app's reference layouts in `src/layouts/` are wired: which file does what, how the pieces connect, and which files are sample data. One section per app. Read an app's section before working on its layouts, and update it in the same change when the wiring changes.

What's elsewhere:

| Looking for | Go to |
| --- | --- |
| Why something looks or behaves as it does; Figma ↔ code decisions | DESIGN.md |
| What the product should do | `prds/` |
| Repo-wide layout rules (sample data and its documented exceptions) | CLAUDE.md "Sample Data" |
| Animation rules and values | MOTION.md, `src/lib/motion/` |
| Component conventions (variants, stories, docs pages) | CLAUDE.md "Creating a Custom Component" |

ℹ️ The apps are listed in CLAUDE.md "Project". Each gets a folder in `src/layouts/<app>/`, and layouts used by more than one app live in `src/layouts/shared/`. Layouts aren't exported from `src/index.ts`. The first layout for a new app adds its section here.

## Writing an app's section

Name the section after the app. Paths in it are relative to `src/layouts/<app>/`. Cover, as tables where items have a name and a short note:

| Part | What it says |
| --- | --- |
| The shell | The app frame every screen shares (navigation, header, page switching) and what state it owns |
| Pages or flows | Each screen's files, how you reach it, and the steps between screens in a flow |
| Sample data | Every `sample-*` file, what it holds and who uses it. Screens never import samples: the stories pass them in. A screen that does is one of CLAUDE.md's documented exceptions, and says so here |
| Layout-only parts | Parts built in the layout because the design system doesn't have them yet. When it does, they move to `src/components/` and are exported |

Layouts shared by more than one app get a `## Shared` section first, with paths relative to `src/layouts/shared/`.

## AutoPartsHUB

Paths are relative to `src/layouts/autopartshub/`. Figma: Sparks (`ShkgoGYA4VmXg8xqfXBZLJ`).

### The shell

`autopartshub.tsx` exports `AutoPartsHubShell`, the frame every AutoPartsHUB page shares: the `background-subtle` page, and `AppHeader` with `AutoPartsHubLogo` on the left and the user's avatar on the right. It takes the `user` (`AutoPartsHubUser`: `firstName`, optional `avatarSrc`) and the page as `children`. It owns no state.

`user-avatar.tsx` exports `UserAvatar`, the signed-in user's avatar, 36px (photo, or the first initial). `header-actions.tsx` exports `HeaderActions`, the right side of the shell's and the Sparks start page's headers: `comments` (the start page: a speech bubble, `unread` for the dot), notifications (a bell, `onNotifications`), then `UserAvatar`; nothing behind comments or notifications yet. `header-icon-button.tsx` exports `HeaderIconButton` (36px ghost, 18px icon, optional `dot`), shared with the concept's header (comments, notifications, close). The concept's header shows `AccessAvatars` (`share-popover.tsx`) beside Share. `SparksWorkspace` takes `comments` (`reviewers`, `unread`, `onOpen`) and opens `CommentsPanel` (`sparks/workspace/comments-panel.tsx`: Review's `ReviewerList` in a `SidePanel`, its reviewers with feedback opening their comment (`onOpen`, `unread`; a reviewer's `comment` is set when they comment), `side-panel.tsx`) on the right, 480px; the stories pass the review's reviewers once it's in review, and `unread`: each reviewer whose latest feedback (comment, then view) she hasn't opened (`onRead`). `notifications-popover.tsx` exports `NotificationsPopover` (the bell with its dot and the popover: Unread and All tabs, "Clear all", read state kept in the popover; `AppNotification`: person, department, success, warning, error or update; `href`, its concept's link, makes the row a link), used by `HeaderActions` and the concept's header; every screen takes `notifications` and the stories pass `sampleNotifications` (`sample-data/sample-notifications.ts`), and route a concept's link with `conceptStoryLinks` (`sparks/start-page/concept-story-links.ts`, shared with the start page's rows): to the workspace story with that concept, in a new tab from the home. A concept's header has neither.

### Pages

- **Home** (`home/home.tsx`, `AutoPartsHubHome`; Figma node 7:1021; PRD: [prds/autopartshub-home.md](prds/autopartshub-home.md)). Renders inside the shell. ### Prototype navigation

The stories link the screens so they can be clicked through in Storybook; the screens themselves only take `href`s and callbacks. `src/layouts/story-links.tsx` (Storybook only) has `goToStory(storyId, args?)`, `withStoryLinks({ href: storyId | { storyId, args, newTab } })` (a decorator that makes a link inside the story open another story), `openStoryInNewTab(storyId, args?)`, `closeStoryTab(fallbackStoryId)` (the story alone, in `iframe.html`) and `storyIds`. Placeholder `#…` links a story doesn't map do nothing. With `args`, the story opens with those args changed once it renders: they show in the Controls panel, and "Reset controls" goes back to the story's own.

- Home → Sparks card (`#sparks`) → Sparks start page in a new tab (`withStoryLinks` with `newTab` and `tab: "autopartshub-sparks"` in `home/home.stories.tsx`): `openStoryInNewTab(storyId, args, tab)` finds the tab by name (`window.open("", tab)`) and, when it's already open, brings it to the front as it is; otherwise it loads the story in it. The screen's card links use `target="autopartshub-{app id}"` for the same in the app. The home names its own tab (`withTabName("autopartshub-home")` in `home.stories.tsx`), so Sparks's "Add from library" (`openStoryInNewTab(autoPartsHubHome, { defaultTab: "library" }, "autopartshub-home")`) brings it back; an open tab gets the args by `postMessage` (`ucl-story-links:show`) and applies them without reloading. The other cards are placeholders and do nothing.
- Sparks start page → a concept's row (its `href`) → Workspace in the same tab, with that concept's name, its step (Review for a concept waiting for a decision, advanced or stopped) and its problem as Dana's first message (`openConcept` in `start-page/start-page.stories.tsx`).
- Sparks start page → "New idea" (`onNewIdea`) → Workspace in the same tab (`goToStory`, its args through sessionStorage) with "New idea" on Plan: Sparks's introduction and nothing else. In the workspace stories, `WorkspacePrototype` (`workspace.stories.tsx`) plays the scripted demo path, one thing at a time: her first message gets `sampleProblemStatementReply` (`sampleProblemMessageKind` sorts it: the demo's problem; too little, `sampleProblemUnclearReply`, asked again; another problem, `sampleProblemFromWordsReply`, her words only, named with `sampleProblemNameFrom`); the first quick reply (or her answer after "Not quite", which folds the card to its question with `answering` set and focuses the message box; Esc in the box calls `onAnswerCancel`, and the story clears `answering`, so the card opens again and focus goes back to its "Not quite") confirms the step (`SparksWorkspace` then folds the card to its question, and `userMessageText` shows the answer in her bubble instead of the quick reply) and brings the next; her answer after "Not quite" goes on the card (`withAnswer`), as an edit does, and a corrected step brings `sampleProblemCorrectedReply(part, problem)` instead, which says what changed and why it matters first (Clarify's and Success's replies do the same for an answer of `"typed"`) (`sampleProblemWhoReply`, which renames the concept to `sampleConceptName`, then `sampleProblemWhyReply`), then `sampleProblemDoneReply(problem)` with her edits (`problemFrom`), which asks Clarify's first question; each answer brings the next of `sampleClarifyNextReplies`, then the brief (`sampleBriefReply`, built by `clarifyAnswers` from her answers); the summaries of the problem, what we know and what success looks like carry the next section in the same reply (`sampleIntoNext` in `plan/sample-section.ts`: the summary, a `section` part (the divider, `SectionBreak`), then the next question or the directions).
